# SFS Multiplayer 服务端：C#/.NET 架构 vs C++ 架构 性能对比

测量平台：ARMv7 Lume（Allwinner T153，四核 Cortex-A7，ARMv7 32 位，`MemTotal 88664 kB`，无 swap）。
采样方式：两边使用**同一个采样脚本**（`board-sample.sh`，2 秒间隔），数值直接读 `/proc/<pid>/status`
与 `/proc/<pid>/stat`；CPU 由 `(utime+stime)` 增量除以墙钟时间得出（HZ=100）。

## 1. 测量条件（结论必须连同这一节一起看）

| | C# 版 | C++ 版 |
|---|---|---|
| 二进制 | `SFS-Multiplayer-Server`（13,487,745 B，self-contained .NET） | `sfs-server-full-arm`（9,038,508 B，静态链接 musl，无运行时依赖） |
| 采样日期 | 2026-09-11 | 2026-09-12 |
| 采样样本 | 125 个（约 260 s） | 30 个（60 s） |
| 存档规模 | **28 火箭 / 296 部件** | 10 火箭 / 151 部件 |
| 连接数 | 1 TCP | 1 TCP |
| 负载性质 | 前段空载 + **后段 4096 箱压测** | 单玩家在线游玩（UDP 活跃） |

> C# 那份样本整体处于**更重**的负载（更大存档 + 4096 箱压测），
> 因此下表的差距应视为**保守下界**，而非夸大值。

## 2. 结果

| 指标 | C# (.NET 8) | C++ | 差距 |
|---|---|---|---|
| **VmRSS 中位数** | **37,644 kB (36.8 MB)** | **2,116 kB (2.07 MB)** | **17.8×** |
| VmRSS 范围 | 36,312 – 41,200 kB | 2,108 – 2,120 kB | — |
| **VmSize 中位数** | **229,860 kB (224 MB)** | **3,356 kB (3.3 MB)** | **68×** |
| **线程数** | 14 – 25（中位 16） | **1** | **16×** |
| **CPU（低负载段）** | 4.13% | **0.08%** | **≈50×** |
| CPU（4096 箱压测段） | 57.77% | 未测 | — |
| 二进制体积 | 13,487,745 B | 9,038,508 B | 0.67×（省 33%） |
| **运行时系统可用内存** | **11.5 MB** | **43.7 MB** | **+32.2 MB** |
| 握手 RTT | 未测 | **1.16 ms** | — |
| Ping/Pong RTT | 未测 | **0.20 ms**（min 0.165 / max 0.307） | — |

## 3. 关键结论

1. **内存是这次换架构的核心收益。** 目标设备总共 88 MB，C# 版常驻 36.8 MB，
   运行时系统只剩 **11.5 MB** 可用 —— 这正是此前一直与内存搏斗的根因。
   C++ 版常驻 2.07 MB，系统可用内存回到 **43.7 MB**，同样的目标设备从"勉强跑"变成"余量充足"。
2. **并发成本低一个数量级。** 单线程 epoll 事件循环替代 CLR 线程池（16 线程中位，
   压测时涨到 25），线程调度与栈占用全部消失。
3. **CPU 占用约 1/50。** 低负载段 4.13% → 0.08%，主要是省掉了 GC 与运行时后台线程的空转。
4. **体积不是主要矛盾。** 只省 33%，因为 C# 那个包是 IL trimming 后的 self-contained；
   真正的差别在运行时内存，而 C++ 版是静态链接、无任何运行时依赖。

## 4. 同负载对比（重载段）

本节是两边**都在高负载档位**时的实测，也是最能说明问题的一组数据。

| | C# 版 | C++ 版 |
|---|---|---|
| 服务端物体数 | **4096 箱** | **8204 枚火箭**（每枚 1 部件） |
| 在线玩家 | 1 | 1 |
| 采样窗口 | 11 s（6 样本） | 81 s（40 样本） |
| 期间客户端流量 | rx 8237 包/s、1430 kB/s | rx 4292 包/s、804 kB/s |

| 指标 | C# 版 @4096 箱 | C++ 版 @8204 物体 | 差距 |
|---|---|---|---|
| **VmRSS** | **38,468 kB (37.6 MB)** | **12,932 kB (12.6 MB)** | **3.0×** |
| VmSize | 295,784 kB | 14,764 kB | **20×** |
| **线程数** | **21** | **1** | **21×** |
| **CPU 占用** | **60.09%** | **19.07%** | **3.2×** |
| **系统可用内存（最低）** | **7,044 kB (6.9 MB)** | **28,684 kB (28.0 MB)** | **+21.6 MB** |
| 协议错误包 | — | **0**（`bad=0`，66 万包累计） | — |

**归一化到「每个物体」的成本**（C++ 承载的物体数是 C# 的 2.0 倍）：

| 每物体成本 | C# 版 | C++ 版 | 差距 |
|---|---|---|---|
| 内存 | **9.39 kB/物体** | **1.58 kB/物体** | **5.9×** |
| CPU | 0.0147% /物体 | 0.0023% /物体 | **6.3×** |

### 这一节的关键含义

- **C# 版的真正瓶颈是系统可用内存**：4096 箱时只剩 **6.9 MB**，
  目标设备处于随时被 OOM Killer 干掉的边缘 —— 这才是当年"内存不够用"的实质。
- **C++ 版装下 2 倍物体后，系统仍剩 28.0 MB**，而且是单线程在扛。
- 折算到每物体，内存低 **5.9 倍**、CPU 低 **6.3 倍**；
  线程从 21 降到 1，调度与线程栈开销整体消失。
- 全程 `bad=0`：8204 物体 + 每秒 4000+ 包的入站解析零错误。

> 数据局限：C# 那段的采样窗口只有 11 s（6 样本），是压测末尾的片段，
> 而 C++ 是 81 s 稳定窗口；且两边**物体数并不相等**（8204 vs 4096）。
> 即便如此 C++ 仍占优，所以结论方向是稳的，但精确倍率应视为量级参考。

## 5. 复现命令

```sh
# 采样（把 PROC 换成目标进程名）
sh board-sample.sh 2 30 > perf.csv

# C# 版采样脚本在 data
# C++ 版派生脚本在 data/logs

# 单个快照
awk '/^VmRSS|^VmSize|^Threads/{print}' /proc/<pid>/status
```
