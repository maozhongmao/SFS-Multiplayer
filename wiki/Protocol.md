# 网络协议

> 本篇给出**报文类型总表**与传输策略；精确的线格式（字段顺序、编码方式）以仓库中的协议实现为准（客户端 `MultiplayerSFS.Common`、服务端 `SfsMultiplayer.Protocol` 为同一份协议定义的两侧实现）。

## 传输策略

- 客户端与服务端之间同时使用 **TCP 与 UDP**：
  - **需要可靠送达的业务包**（进入/退出、火箭创建与销毁、控制权、对接、聊天等）走可靠通道；
  - **高频状态包**（火箭位姿、部件状态、时间）走 UDP，按类型分流；
  - UDP 不可用时，使用 TCP 进行必要的状态同步，保证基本可玩；
- UDP 绑定带**固定间隔心跳重试**：绑定丢失后自动恢复，不需要重连整条连接；
- 玩家之间建立**直连通道（P2P）**后，两名玩家之间的火箭状态不再绕经服务端；直连中断自动回退到服务端中转（见 [联机架构](Architecture)）。

## 会话流程（简）

```text
客户端                                   服务端
  │  1) 发起连接 / 建立 UDP 绑定            │
  │ ──────────────────────────────────────► │
  │  2) JoinRequest（用户名等）              │
  │ ──────────────────────────────────────► │  校验：密码、重名、人数上限、输入边界
  │  3) JoinResponse（玩家 ID + 初始世界）   │
  │ ◄────────────────────────────────────── │
  │  4) PlayerConnected（广播给其他人）      │
  │ ◄────────────────────────────────────── │
  │  5) 进入世界：状态包与业务包开始双向流动  │
```

- 服务端为每个连接分配会话与玩家身份，并**为每名玩家分配状态更新权威**；
- 断线后重连需要重新握手；同一时刻只应有一个服务端实例监听同一端口。

## 幂等与去重

- 客户端发出的**创建请求带本地 ID**；服务端按「玩家 + 本地 ID」去重，重复到达时复用同一枚火箭，不会因为重发而多出一枚；
- 状态包按"同一对象只保留最新"处理：服务端状态队列对同一枚火箭只保留最新一条，避免慢客户端积压过期状态。

## 排障提示

- 若高频状态包能到、业务包丢失，表现为"位置动但操作不生效"，优先检查链路是否需要可靠通道分流；
- 若两端版本不匹配，握手阶段就会失败，不要试图靠重连绕过；
- 具体字段级问题请附上客户端日志（可用 `UploadLog` 上报）与服务端日志，便于定位。
